ВВЕДЕНИЕ
Подводные роботы всё шире применяют для обследования сооружений, съёмки рельефа дна и научных работ там, где человеку либо опасно, либо технически трудно находиться [1]. Для автономных необитаемых подводных аппаратов (АНПА) типичной является работа по заранее заданному списку путевых точек с удержанием глубины и устойчивым движением в горизонтальной плоскости [2].
Отладку программ управления чаще начинают не в море: натурные испытания дороги, дологи в подготовке и не свободны от риска для аппарата. Симулятор даёт возможность многократно прогонять один и тот же сценарий и сравнивать разные настройки регуляторов. В курсовом проекте используется MUR IDE [3] — среда на Python с трёхмерной моделью MiddleAUV; связь с моделью выполняют через pymurapi [4].
В проекте разрабатывают программу для MUR IDE, которая ведёт АНПА по заданным координатам (x, y, глубина), записывает параметры движения в файл и строит график траектории с отметками путевых точек.
Для достижения цели в работе ставятся задачи:
— провести анализ возможностей MUR IDE и pymurapi с учётом ограничений по измерению положения аппарата;
— сформулировать требования к формату путевых точек, структуре данных и логу;
— спроектировать модульную архитектуру (waypoints, навигация, управление, логирование, визуализация);
— реализовать основной цикл управления с частотой 10–20 Гц, пропорциональные регуляторы курса и глубины;
— выполнить испытания на типовых траекториях (прямая, квадрат, треугольник, ломаная), оценить точность и влияние настроек.
Объект исследования — программные средства навигации и управления АНПА в симуляторе. Предмет — алгоритмы последовательного прохода путевых точек, расчёт целевого курса и расстояния до цели, запись телеметрии и построение графиков траектории.

1 СИСТЕМНЫЙ АНАЛИЗ И ПОСТАНОВКА ЗАДАЧИ
1.1. Анализ доступных средств симулятора MUR IDE для получения координат и управления аппаратом.
MUR IDE — среда разработки для MiddleAUV и MiddleUSV со встроенным симулятором. Сценарии на Python запускают из редактора; это типичный для учебы способ быстро менять код и смотреть результат на модели.
Режимов несколько: работа с реальным аппаратом по сети, телеуправление, локальный запуск скрипта рядом с симулятором на ПК. В проекте опираются на локальный режим: он не требует носителя и позволяет отладить логику миссии на модели.
Симулятор учитывает инерцию и сопротивление среды [5], реакция на моторы не мгновенная, поэтому коэффициенты П-регуляторов подбирают с запасом по времени. Из pymurapi читают, в частности, курс (yaw) и глубину; мощность движителей задают в условных единицах порядка −100…+100.
Для обхода путевых точек в плане нужны координаты x, y. В распространённой конфигурации симулятора они не всегда приходят в телеметрии непрерывно — тогда оценку положения строят по одометрии: на каждом шаге цикла наращивают пройденный путь из курса и принятой скорости. Если в сборке pymurapi есть get_x и get_y, можно перейти на них и не использовать мёртвое счисление. Оба варианта укладываются в схему «курс + глубина» при неполных данных о месте в плане.
Команды моторов начинают двигать модель только после включения Remote mode в окне симулятора; иначе аппарат ведёт себя как свободное тело сцены, и сценарий на него не действует.
1.2. Определение формата задания путевых точек.
Путевая точка задаётся координатами в системе отсчёта сцены и глубиной (ось Z, положительная вниз, в согласовании с показаниями глубиномера в pymurapi). Маршрут — упорядоченный список точек; аппарат последовательно выполняет переход к текущей цели, затем к следующей. Поддерживается задание полного обхода маршрута несколько раз (циклы): после последней точки индекс снова указывает на первую.
Формат обмена с пользователем и внешними средствами: текстовый файл CSV с тремя полями в строке — X, Y, Z (глубина); допускается строка заголовка с буквенными обозначениями столбцов. Альтернатива — массив координат, заданный непосредственно в исходном коде программы. При чтении CSV выполняется проверка числа столбцов, преобразования в вещественные числа и неотрицательности глубины.
Для активной цели в алгоритме управления используются горизонтальные координаты цели и аппарата (или их оценки) для вычисления дистанции и азимута; удержание глубины — по значению Z из соответствующей путевой точки. Управление по курсу при постоянной тяге вперёд типично для простых алгоритмов waypoint-навигации; боковой снос при ошибках курса в такой схеме не компенсируется отдельным контуром по положению.
1.3. Выбор структуры данных для хранения точек и логирования.
Для хранения маршрута в программе используется список кортежей вида (x, y, z) в порядке прохождения; тип задаётся средствами языка Python [9]. Менеджер маршрута (класс в модуле waypoints) дополнительно хранит индекс текущей точки, число завершённых циклов, параметры зоны достижения точки (радиус схватывания, допуск, при необходимости — параметр внешнего «кольца подхода» для гистерезиса) и предоставляет методы current, advance_if_reached, is_finished, оценку прогресса в процентах.
Файл лога реализуется как CSV: первая строка — заголовок с именами полей (время, координаты x и y по оценке или из API, глубина, курс, расстояние до цели, при необходимости целевой курс, мощности двигателей и др. — в объёме, достаточном для отчёта и графиков). Последующие строки — показания с фиксированным интервалом, согласованным с требованием периодической записи (например, порядка одной секунды) при сохранении отдельного такта управления 10–20 Гц. Имя файла лога может включать отметку даты и времени создания для различения серий испытаний.
1.4. Формализация требований к программе и показателям качества движения.
Программа должна функционировать в среде MUR IDE на языке Python с использованием pymurapi [4].
Модуль задания путевых точек: хранение списка в формате (x, y, z); задание в коде или загрузка из текстового файла CSV; возможность задания числа циклов прохождения маршрута.
Модуль навигации: оценка или чтение текущих координат; расчёт евклидова расстояния до текущей цели в плоскости OXY; расчёт целевого курса через арктангенс двух аргументов; переключение на следующую точку при выполнении условия достижения (расстояние меньше заданного порога с учётом допусков); учёт вырожденного вектора к цели (малые dx, dy), чтобы не вызывать atan2(0, 0).
Модуль управления: пропорциональный регулятор курса [6] с разнесением тяги по бортовым движителям при движении вперёд; пропорциональный регулятор глубины для вертикальных движителей; ограничение управляющих сигналов допустимым диапазоном pymurapi. Обоснование выбора П-регулятора: простота реализации и настройки в учебном симуляторе при отсутствии требований к устранению статической ошибки; при необходимости структура может быть расширена до ПИД.
Модуль логирования: периодическая запись в CSV полей в согласованном с п. 1.3 составе; фиксация моментов смены путевой точки (по усмотрению разработчика).
Модуль визуализации: вывод ключевых величин в консоль во время миссии; после завершения — построение графика траектории (библиотека matplotlib) с отображением фактического пути и путевых точек.
Показатели качества движения: среднее и максимальное отклонение фактической траектории от ломаной по путевым точкам, время прохождения маршрута, отсутствие незатухающих колебаний курса и глубины при типовых коэффициентах, успешное достижение всех точек сценария.
1.5. Определение сценариев тестирования.
Для проверки программы используют четыре простых типа траектории. Прямая — минимум две точки, оценка устойчивости курса и глубины на вытянутом участке. Квадрат — четыре точки по вершинам, контроль поворотов около 90° и накопления ошибки одометрии при замыкании контура. Треугольник — три вершины, более острые углы относительно квадрата. Ломаная — несколько звеньев с разными азимутами, проверка устойчивости при частой смене целевого направления. Для каждого сценария задаются файлы координат или списки в коде, глубина, число циклов, коэффициенты регуляторов и радиус схватывания.

2 ПРОЕКТИРОВАНИЕ ПРОГРАММЫ ДЛЯ ПОСТРОЕНИЯ И ВИЗУАЛИЗАЦИИ ТРАЕКТОРИИ ДВИЖЕНИЯ АНПА ПО ТОЧКАМ В СИМУЛЯТОРЕ MUR IDE
2.1. Разработка общей архитектуры программы.
Программа разделена на логические модули: задание и обход путевых точек (waypoints.py), расчёты навигации (navigation.py), формирование команд двигателям (control.py), шаг одометрии при отсутствии координат из API (odometry.py), запись лога (logger_module.py), построение графиков (visualize.py) и главный сценарий миссии (waypoint_mission.py), который связывает перечисленные части. Сценарий инициализирует pymurapi, загружает маршрут, в цикле обновляет оценку положения, запрашивает телеметрию, вызывает расчёты навигации и управления, по таймеру пишет в журнал; по окончании миссии закрывает лог и при необходимости запускает визуализацию по сохранённому CSV. Модули навигации и управления не содержат обращений к симулятору — только чистые функции и классы, которым из waypoint_mission передают числовые данные. 2.2. Проектирование модуля задания и хранения путевых точек.
Маршрут представляется списком кортежей (x, y, z). Класс-менеджер хранит текущий индекс, число завершённых циклов, параметры схватывания. Радиус схватывания capture_radius задаёт базовую зону «у цели»; к нему добавляется допуск reach_slack_m, чтобы учесть дрожание оценки расстояния (одометрия или шум) и не застревать бесконечно на границе круга.
Для предотвращения ложного немедленного перехода ко второй точке при старте у первой цели в начале координат вводится гистерезис: фиксируется факт «подхода снаружи», если расстояние превышало меньший порог approach_ring_m (кольцо подхода), после чего при попадании в объединённый порог capture_radius + reach_slack_m точка считается достигнутой. Условие approach_ring_m < capture_radius + reach_slack_m гарантирует, что при колебаниях расстояния около цели внешний порог хотя бы раз будет выполнен при реалистичной амплитуде колебаний одометрии.
Реализуется загрузка CSV: три столбца координат, проверка корректности чисел, неотрицательной глубины, обработка заголовка; при ошибке — сообщение пользователю и переход к маршруту по умолчанию.
2.3. Проектирование модуля навигации.
Расстояние до текущей целевой точки (xц, yц) от оценённого положения (x, y):
d = √((xц − x)^2 + (yц − y)^2).
Целевой курс (азимут на цель):
ψц,рад = atan2(yц − y, xц − x),
ψц = ψц,рад · 180/π (градусы, согласованные с датчиком курса в симуляторе).
Ошибка курса eψ как кратчайший поворот к цели, в градусах, с ограничением по модулю 180°:
eψ = atan2(sin((ψц − ψ) · π/180), cos((ψц − ψ) · π/180)) · 180/π
(эквивалентно приведению разности ψц − ψ к отрезку от −180° до 180°, чтобы избежать избыточного разворота вместо минимального).
При очень малом |dx| + |dy| или длине вектора к цели ниже порога BEARING_DEGENERATE не вызывается atan2(0,0); сохраняется устойчивый целевой курс для участка «у цели».
2.4. Проектирование модуля управления.
Горизонтальное движение: базовая тяга «вперёд» на оба бортовых движителя и корректирующая добавка пропорционально ошибке курса: при положительной ошибке, требующей поворота в одну сторону, увеличивается тяга на соответствующем борту и уменьшается на другом (или по согласованной схеме знаков в коде). Сигналы ограничиваются по модулю допустимым диапазоном для set_motor_power.
Вертикальное удержание глубины: ошибка по глубине ez = z − zц, где z — текущая глубина, zц — целевая из waypoints; закон u_depth = −Kp_depth · ez с насыщением сигнала на движители 2 и 3 (или иная нумерация по принятой схеме аппарата в симуляторе).
При необходимости для учебной модели обнуляется неиспользуемый четвёртый двигатель, чтобы он не вносил лишний момент.
2.5. Проектирование модуля логирования.
В журнал пишут всё, что потребуется потом для графика и оценки качества: время от старта, X и Y (из API или одометрии), глубину, курс, целевой курс, дистанцию до активной точки, команды на четыре мотора, номер точки в маршруте. По смене номера точки в столбце видно, как шло сближение с каждой вершиной; отдельную колонку «событие» для этого не обязательно заводить, если шаг записи не слишком редкий.
Пишут в CSV реже, чем крутят цикл управления: при 10 Гц цикла разумна запись около раза в секунду — файл не раздувается, а для RMSE и графиков данных хватает. Файлы складывают в подкаталог logs; в имя добавляют дату и время, чтобы прогоны не затирали друг друга. Заголовки делают по-русски в UTF-8; при записи из Python у csv.writer обычно отключают лишний перевод строки в параметре newline, иначе в файле появляются пустые строки.
2.6. Проектирование модуля визуализации.
Для чертежей в записке используют matplotlib [8]: нужен график в плане OXY с фактическим путём и путевыми точками. Программа читает свой же CSV по именам столбцов. На одном поле рисуют полилинию факта, маркеры точек и пунктир между точками по порядку маршрута (у замкнутого контура последнюю точку иногда соединяют с первой, чтобы контур был виден целиком). Оси X и Y масштабируют одинаково, иначе углы на графике «лгут». Сетку и легенду оставляют включёнными; для вставки в Word или на плакат сохраняют PNG с высоким разрешением (около 300 dpi). При необходимости отдельно строят глубину от времени по тому же логу.

3 РЕАЛИЗАЦИЯ ПРОГРАММЫ ДЛЯ ПОСТРОЕНИЯ И ВИЗУАЛИЗАЦИИ ТРАЕКТОРИИ ДВИЖЕНИЯ АНПА ПО ТОЧКАМ В СИМУЛЯТОРЕ MUR IDE
3.1. Настройка среды разработки и подключение к симулятору.
Устанавливают и запускают MUR IDE, открывают сцену с MiddleAUV [12]. В окне симулятора включают Remote mode. Сценарий waypoint_mission.py открывают в проекте или стартуют из консоли среды.
Подключение выполняется вызовом mur_init(); при возврате None выводится сообщение об ошибке и выполнение прекращается:
import pymurapi as mur
auv = mur.mur_init()
if auv is None:
    print("Ошибка: не удалось подключиться к симулятору")

Перед первой серией прогонов на новой машине клонируют исходники MUR с GitHub (mur_ide и mur_simulator), при необходимости собирают симулятор по инструкции проекта и прописывают в настройках MUR IDE пути к resources, интерпретатору Python и бинарнику симулятора. Ресурсы сцены лежат в mur_simulator/resources/Data/, примеры сценариев — в mur_ide/resources/examples/waypoint_mission/. В отчёте имеет смысл указать ветку или коммит, версию MUR IDE и фактические пути к каталогам — так проще воспроизвести результат.
3.2. Реализация базовых функций работы с аппаратом.
Чтение курса и глубины, запись мощностей на моторы делают через pymurapi: get_yaw(), get_depth(), set_motor_power(номер, мощность). Горизонтальные координаты в телеметрии бывают недоступны; тогда в сценарии пробуют get_x()/get_y() в try/except и при неудаче считают положение одометрией.
Одометрия вынесена в odometry.py. Шаг dt берут как разницу по часам между итерациями, ограничивая сверху, чтобы после паузы не получить один огромный скачок. Скорость в плане связывают со средней командой на моторы 0 и 1 предыдущего шага: v = (0,5·(m0 + m1)/100)·ODOMETRY_SPEED_SCALE; сам множитель ODOMETRY_SPEED_SCALE в работе подгоняют по тому, как на экране и в логе убывает расстояние до цели. Курс берут из get_yaw(). Начальные координаты x и y в оценке задают нулями, если нет API; глубину всё равно читают с get_depth().
3.3. Реализация модуля навигации.
В navigation.py собраны функции без обращения к симулятору. calculate_distance даёт расстояние между точками. calculate_target_yaw — азимут на цель через atan2. В calculate_target_yaw_near_aware учтён почти нулевой вектор к цели: иначе atan2(0,0) даёт нулевой целевой курс, и у вершины аппарат «съезжает» тангентой; при малом |dx|, |dy| целевой курс временно оставляют текущим. normalize_angle и calculate_yaw_error приводят разницу курсов к диапазону ±180°. distance_to_waypoint оборачивает расчёт дистанции до активной точки.
Порог «почти нулевого» вектора в коде согласован с константой основного цикла (BEARING_DEGENERATE_M), чтобы не путаться в настройках между текстом записки и программой.
В основном цикле обычно идут так: оценка позиции, дистанция до текущей точки, целевой курс с учётом вырождения, затем передача углов в контур управления (см. п. 2.3).
3.4. Реализация пропорциональных регуляторов.
В control.py считают ошибки по курсу и глубине и собирают команды на четыре мотора с ограничением по модулю. Конфигурация сознательно близка к примерам sim_yaw_preg и sim_depth_preg из репозитория MUR [10]: базовая тяга около 40 у. е., П-закон по курсу (в реализации — через разнесение моторов 0 и 1), от лида по глубине на моторы 2 и 3. Конкретные коэффициенты смотрят в коде; в записке достаточно ориентиров: усиление по курсу подбирают по отсутствию зигзага на прямой и по аккуратности поворотов, по глубине — по отсутствию длительных качаний около заданной отметки.
Фрагмент идеи расчёта горизонтальных моторов (пояснительно, ψ — текущий курс, ψц — целевой из навигации):
eψ = atan2(sin((ψц − ψ) · π/180), cos((ψц − ψ) · π/180)) · 180/π
u = max(−35, min(35, −Kp_yaw · eψ))
Mleft = max(−100, min(100, M0 − u)), Mright = max(−100, min(100, M0 + u))
(M0 — базовая тяга «вперёд», ограничение по каналам — типично ±100 условных единиц pymurapi.)
3.5. Реализация основного цикла программы.
Скрипт waypoint_mission.py загружает waypoints из файла waypoints.csv рядом со скриптом или использует встроенный список по умолчанию. Создаётся WaypointManager с параметрами capture_radius, reach_slack_m, approach_ring_m, cycles.
Константы частоты: UPDATE_HZ = 10, UPDATE_DT = 1 / UPDATE_HZ; в цикле time.sleep(UPDATE_DT).
Пока менеджер не сообщил о завершении всех циклов: получить телеметрию; обновить позицию; взять текущую цель; вычислить d и целевой курс; вычислить команды; применить к моторам; вызвать advance_if_reached(d); при необходимости вывести в консоль номер точки, дистанцию, курс, глубину; выполнить log по таймеру.
Завершение: закрыть файл лога; при необходимости вызвать visualize.
3.6. Реализация модуля логирования.
В logger_module.py логгер оформлен классом на базе dataclass. При создании объекта создают каталог logs и новый файл с префиксом trajectory_log_ и отметкой времени в имени. Запись ведут в UTF-8: первая строка — заголовки столбцов на русском (время, координаты, курсы, расстояние, четыре мощности, номер точки). Метод log дописывает строку с показаниями и временем от старта логгера; close закрывает файл. В основном цикле log вызывают не на каждом шаге, а с интервалом около секунды (LOG_INTERVAL), чтобы при управлении 10 Гц не раздувать CSV.
3.7. Реализация модуля визуализации.
В visualize.py журнал читают через csv.DictReader (pandas не используют). load_log возвращает списки времён и координат. На matplotlib строят план X–Y с равными осями: фактическая траектория сплошной линией, путевые точки маркерами, маршрут — пунктиром; для замкнутого контура последнюю точку часто соединяют с первой, чтобы контур был виден целиком. Фигуру сохраняют в PNG с высоким dpi; при необходимости отдельно строят глубину от времени. После прогона модуль запускают вручную, задавая путь к CSV и к выходному изображению.

4.2. Оценка точности движения:
После прогонов по сценариям раздела 1.5 (прямая, квадрат, треугольник, ломаная) разбирают журналы и графики. Используют столбцы CSV (время, координаты, курс, глубина, расстояние до цели), наблюдение в окне симулятора и совмещённые планы эталона и факта (рис. 4.22–4.25).
Для количественной оценки используют среднеквадратичное отклонение фактической траектории от эталонной ломаной и при необходимости максимальное отклонение по горизонтали. Пусть по логу получены n выборок (xi, yi), i = 1…n, а (xi,эт, yi,эт) — соответствующие опорные координаты на эталонной ломаной (например, ближайшая точка на отрезках между waypoints или интерполяция эталонного маршрута по длине пути). Тогда величина RMSE определяется по формуле [11]:
RMSE = √((1/n) · Σi ((xi − xi,эт)² + (yi − yi,эт)²)).
Где: n — число учтённых точек выборки; xi, yi — координаты из лога; xi,эт, yi,эт — координаты эталона на плоскости OXY.
При использовании одометрии без прямых координат из API абсолютная привязка траектории к метрам сцены зависит от выбранного ODOMETRY_SPEED_SCALE; поэтому наряду с RMSE используют согласование дистанции до цели с поведением на экране и визуальное наложение на графиках. Дополнительно фиксируют время прохождения полного маршрута, число успешно достигнутых путевых точек, отсутствие застревания индекса точки при колебаниях расстояния у порога схватывания.

нелинейность и насыщение по мощности — скорость в горизонтальной плоскости не пропорциональна тяге линейно, разность моторов ограничена;
погрешность одометрии и масштаба ODOMETRY_SPEED_SCALE — при отсутствии прямых X, Y из телеметрии горизонтальное положение носит оценочный характер;
колебания оценки расстояния до точки у границы зоны схватывания — влияет на момент переключения на следующую вершину и на вид траектории у цели.
4.3. Настройка коэффициентов регуляторов для улучшения качества движения.
Подбор выполняют в той же среде MUR IDE и на той же сцене, что и основные испытания, чтобы сравнение наборов параметров было корректным. В рамках реализации, согласованной с учебными примерами sim_yaw_preg и sim_depth_preg, для базового варианта приняты значения: базовая тяга «вперёд» на горизонтальные моторы 40 условных единиц; формирование разнесения мощностей по курсу с коэффициентом по ошибке курса 0,8 и ограничением модуля добавки к разности моторов 28 условных единиц; контур глубины с коэффициентом 80 на ошибку глубины в метрах, с подачей команды на вертикальные моторы по схеме симулятора. Эти величины задаются в модуле control.py и при необходимости изменяются в ходе настройки.
При слишком малом усилении по курсу аппарат медленно разворачивается, траектория срезает углы с большой хордой, время выхода на новый азимут растёт. При избыточном усилении возрастают колебания курса и зигзаг на прямых. По глубине малый коэффициент даёт долгий выход на целевую отметку, большой — склонность к перерегулированию и колебаниям по глубине. Настройка выполняется серией прогонов на одном из типовых маршрутов (удобно квадрат или прямая): фиксируют графики или фрагменты журнала, сравнивают два-три набора коэффициентов. Для отчёта допускается отдельный рисунок или плакат — с наложением траекторий или эпюрами курса и глубины при разных настройках.
4.4. Анализ влияния радиуса схватывания на точность прохождения точек.
Радиус схватывания capture_radius задаёт основную геометрическую зону у цели. При слишком малом радиусе без достаточного допуска reach_slack_m аппарат при одометрической дрожи расстояния (типично сантиметры) может долго оставаться вблизи точки, не выполняя условие перехода к следующей; в отчёте это проявляется как рост времени миссии и застревание номера точки в журнале. Слишком большой эффективный порог (capture_radius плюс reach_slack_m) ускоряет переключение, но снижает геометрическую точность остановки у вершины: точка считается достигнутой, когда аппарат ещё заметно не совпал с вершиной ломаной.
Параметр reach_slack_m расширяет зону достижения и сглаживает колебания оценки дистанции у границы. Параметр approach_ring_m (кольцо подхода, меньше эффективного внутреннего схватывания) реализует гистерезис: требуется хотя бы раз оказаться снаружи относительно этого кольца, прежде чем сработает переключение при входе в полную зону. Это снимает ложный мгновенный переход со старта, когда первая цель совпадает с началом координат и оценка расстояния мала, и уменьшает риск циклирования при дрожи расстояния. Условие согласования порогов: параметр approach_ring_m должен быть меньше суммы capture_radius и reach_slack_m.
Удобно сравнить два-три набора (capture_radius, reach_slack_m, approach_ring_m) на одном waypoints.csv, зафиксировать время прохода и вид траектории у вершин; при необходимости вынести цифры в приложение или подписать под рисунками.
4.5. Сравнение полученных траекторий с заданными.
Для визуальной оценки точности движения по каждому сценарию из пункта 1.5 строят совмещённые графики на плоскости OXY. На одном и том же чертеже отображают заданную траекторию (путевые точки и ломаная между ними — эталон) и фактический путь по столбцам X и Y CSV-журнала, полученного при соответствующем прогоне в симуляторе MUR IDE. Такой формат совпадает с построением, выполняемым модулем визуализации: фактическая траектория сплошной линией, точки маршрута маркерами, соединение точек пунктиром для наглядного сравнения с ломаной. Расчётные RMSE и максимальные отклонения по сценариям сводят в таблицу 4.1.
Рисунки 4.22–4.25 — совмещённые планы прямой, квадрата, треугольника и ломаной; ниже коротко описано, как факт ложится на эталон (отклонения — по табл. 4.1 и записям в журнале).


Рисунок 4.22 – Совмещённый график траектории «прямая» (заданная ломаная и фактический путь по логу)

По рисунку 4.22: на прямой из двух и более точек в одном направлении траектория обычно близка к отрезку между крайними целями; расхождения заметны на разгоне, выходе на курс и у финиша — инерция и одометрия. При удачном ODOMETRY_SPEED_SCALE сплошная линия факта почти совпадает с пунктиром эталона; сдвиг вдоль маршрута намекает на подстройку масштаба одометрии.


Рисунок 4.23 – Совмещённый график траектории «квадрат»

По рисунку 4.23: четыре стороны замкнутого квадрата; на плане обычно видно следующее:
прямые участки — движение близко к отрезкам эталона, отклонения по нормали к стороне обычно меньше, чем в углах;
угловые точки — у вершин видны срез угла или «скругление» из-за запаздывания поворота курса и ограничения по мощности;
накопление ошибки одометрии — к последним сторонам возможен сдвиг всей фактической линии относительно эталона, что заметно при сравнении замыкания контура с первой вершиной.


Рисунок 4.24 – Совмещённый график траектории «треугольник»

По рисунку 4.24: у треугольника поворотов меньше, чем у квадрата, и при тех же настройках три звена часто ложатся на эталон чуть ровнее; острые углы дают локальные отходы факта от ломаной. После поворота на следующем отрезке точность может временно просесть, пока курс не успокоится.


Рисунок 4.25 – Совмещённый график траектории «ломаная линия»

По рисунку 4.25: ломаная с разными азимутами нагружает контур курса частыми переключениями; смотрят, нет ли лишнего зигзага между соседними точками. Участки, где соседние звенья почти противоположны по направлению, обычно дают самое заметное расхождение факта с пунктиром.

Графики 4.22–4.25 вносят на плакат А1 (прямая, квадрат, треугольник, ломаная); рядом можно дать RMSE из табл. 4.1 или саму таблицу. Отдельным плакатом А1 иногда показывают два-три варианта настройки схватывания или усиления по курсу на одном маршруте (например, квадрат) — как в п. 4.3 и 4.4.

ЗАКЛЮЧЕНИЕ
В курсовом проекте разобрана задача ведения АНПА по путевым точкам в MUR IDE и сформулированы требования к программе. Программа собрана из модулей: маршрут, навигация (с одометрией, если в телеметрии нет прямых x, y), П-регуляторы курса и глубины, лог и визуализация.
Для переключения точек использован гистерезис (кольцо подхода и порог с допуском), что уменьшает ложные срабатывания при дискретном управлении и дрожании оценки дистанции. Испытания на простых траекториях показали, что схема «курс + глубина» работает при разумной настройке коэффициентов и ODOMETRY_SPEED_SCALE.
Практический итог — связка готовых модулей под MUR IDE; на её базе можно дальше добавить ПИД, опираться на координаты API, если они есть, ввести фильтрацию и более сложные правила смены сегментов пути.
